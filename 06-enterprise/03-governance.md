# 6.3 Governance: ควบคุมสิทธิ์ Audit และข้อควรระวังองค์กร

> ระดับ: 🔴 Advanced | สำหรับ: BI lead, Data Governance team, และคนที่ต้องตอบคำถามผู้บริหาร/audit

เทคนิคทั้งหมดพร้อมแล้วจากบทก่อน ๆ — บทนี้คือชั้น **นโยบายและกระบวนการ** ที่ทำให้การใช้ AI กับข้อมูลองค์กร "อธิบายได้และตรวจสอบได้"

## คำถาม 5 ข้อที่ต้องตอบได้ก่อน Rollout

### 1. ใครใช้ได้ และเห็นอะไร

- นิยามกลุ่มผู้ใช้ + data source ที่เปิดให้แต่ละกลุ่ม — อย่าเปิด "ทั้ง site" เป็นค่าตั้งต้น เริ่มจาก data source ที่ curate แล้ว (นิยามชัด, description ครบ, RLS ทดสอบแล้ว) ค่อยขยาย
- กลไก: Tableau permission ปกติ + สถาปัตยกรรม credential จากบท 4.2 — governance ของ MCP ที่ดีที่สุดคือ governance ของ Tableau ที่ดีอยู่แล้ว MCP ไม่ได้สร้างระบบสิทธิ์ใหม่ มันสะท้อนของเดิม (รวมทั้งจุดอ่อนของเดิมด้วย!)

### 2. ข้อมูลไหลไปไหนบ้าง

จุดที่ต่างจาก dashboard ปกติ: ผลลัพธ์ query **เข้าไปอยู่ในบทสนทนากับ AI** — ต้องตอบ compliance ให้ได้ว่า:

- ใช้ผ่านช่องทางไหน: Claude consumer app / Claude for Work / API — เงื่อนไขการเก็บและใช้ข้อมูลต่างกัน อ่านของจริงจากเอกสาร Anthropic + ให้ legal ทวน อย่าฟังต่อ ๆ กันมา
- ข้อมูลระดับไหน "ห้ามผ่าน AI" — ทุกองค์กรควรมี list นี้เป็นลายลักษณ์ (เช่น ข้อมูลส่วนบุคคลอ่อนไหว, ดีล M&A) และบังคับด้วยการไม่เปิด data source เหล่านั้นให้ MCP เห็นตั้งแต่ระดับ permission ไม่ใช่หวังพึ่งวินัยผู้ใช้
- PDPA: ถ้า data source มีข้อมูลส่วนบุคคล การ query ผ่าน AI = การประมวลผลรูปแบบหนึ่ง — ให้ DPO เข้ามาดูตั้งแต่ design ไม่ใช่หลัง rollout

### 3. ตรวจย้อนหลังได้อย่างไร

ผูก 3 ชั้น log ที่มีอยู่แล้วให้เป็นเรื่องเดียว:

| ชั้น | ได้จาก | ตอบคำถาม |
|---|---|---|
| ใครถามอะไร | แอปของเรา (บท 5.3) หรือ log ฝั่ง Claude for Work | "ใครเป็นคน query" |
| Tool call + arguments | MCP/แอป log (บท 6.1 ชั้น 7) | "query อะไรเกิดขึ้นจริง" |
| ฝั่ง Tableau | Tableau audit/admin views | "Tableau เห็น access จากใคร เมื่อไหร่" |

กำหนด retention ให้สอดคล้องนโยบาย audit ที่มีอยู่ (เช่น 90 วัน - 1 ปี)

### 4. เชื่อคำตอบได้แค่ไหน (Accuracy Governance)

ความเสี่ยงเฉพาะของ BI+AI: คำตอบผิดที่ **ฟังดูมั่นใจ** — มาตรการที่ได้ผลจริง:

- **นโยบาย "ตัวเลขสำคัญต้องมี query แนบ"** — ใช้ output template บท 4.1 บังคับใน system prompt ให้ทุกคำตอบระบุ field + filter
- **Certified data source first** — เปิดใช้เฉพาะ data source ที่ผ่านการรับรอง นิยาม metric ตรงกับที่องค์กรใช้
- **แยกระดับการใช้:** สำรวจ/ร่าง = ใช้อิสระ | ตัวเลขเข้าที่ประชุมผู้บริหาร/ส่งภายนอก = ต้องมีคน verify — เขียนเส้นนี้เป็นนโยบาย 1 บรรทัด ช่วยตัดดราม่าได้มาก
- ให้ user รายงาน "คำตอบเพี้ยน" ง่าย ๆ (form/แชนแนลเดียว) → ทีม BI ใช้ปรับ prompt, metadata, หรือ custom tool

### 5. ใครดูแล และวัดผลด้วยอะไร

- **Owner ชัดเจน 1 ทีม** (มัก BI/Analytics) ดูแล: MCP infra, system prompts, การเปิด data source เพิ่ม, รอบอัปเกรด (บท 6.2)
- กระบวนการขอเปิด data source ใหม่: checklist สั้น ๆ — RLS ทดสอบแล้ว? description ครบ? เจ้าของข้อมูลอนุมัติ? — ผ่านแล้วค่อยเข้า INCLUDE list
- วัดผลรายไตรมาส: จำนวนผู้ใช้ active, คำถาม/สัปดาห์, อัตรารายงานคำตอบเพี้ยน, เวลาที่ทีม data ประหยัดจาก ad-hoc request ที่หายไป

## Rollout แบบเป็นขั้น (แนะนำจากประสบการณ์จริง)

```
Phase 1 (2-4 สัปดาห์): ทีม data ใช้เอง
  → เก็บ pattern คำถาม, จูน metadata + prompts, ทดสอบ RLS
Phase 2 (1-2 เดือน): Pilot 10-20 power users จาก 2-3 แผนก
  → data source ที่ curate แล้วเท่านั้น, ประชุม feedback รายสัปดาห์
Phase 3: ขยายตามแผนก พร้อม onboarding สั้น ๆ (สอน pattern บท 4.1!)
  → governance ครบทั้ง 5 ข้อข้างบนก่อนเข้า phase นี้
```

ข้อผิดพลาดยอดฮิต: กระโดดเข้า Phase 3 เพราะ demo สวย — แล้วเจอคำถามข้อ 2-4 ตอบไม่ได้กลางทาง โดนหยุดโครงการ ซึ่งเสียแรงกว่าทำ Phase 1-2 ให้ครบมาก

## เอกสารขั้นต่ำที่ควรมี

1. **AI Data Access Policy** (1-2 หน้า): ใครใช้ได้, data ระดับไหนผ่านได้, ระดับการ verify ตัวเลข
2. **RLS Test Report** (จากบท 4.2): หลักฐานทดสอบ 4 case ต่อ data source
3. **Runbook** (จากบท 6.2): ปฏิบัติการและเหตุฉุกเฉิน
4. **Data Source Onboarding Checklist**: เกณฑ์ก่อนเปิด data source ใหม่เข้า MCP
