# 6.4 POC Checklist: ทำ Proof of Concept ให้องค์กร

> ระดับ: 🔴 Advanced | สำหรับ: consultant, ทีมที่ต้องพิสูจน์คุณค่าให้ผู้บริหารเห็นก่อนลงทุนจริง

POC ที่ดีไม่ใช่ demo ที่ว้าวที่สุด — คือ POC ที่ **ตอบคำถามการตัดสินใจ** ขององค์กรได้ครบ บทนี้คือ playbook ที่ใช้ได้ทั้งฝั่งทำเองภายในและฝั่ง consultant เสนอลูกค้า

## Phase 0: ตกลงเป้าก่อนแตะเทคโนโลยี (สำคัญสุด)

นั่งกับ sponsor ตอบ 3 ข้อให้ได้เป็นลายลักษณ์:

1. **Use case นำร่อง 2-3 อัน** ที่มีเจ้าของปัญหาจริง — เช่น "ทีมขายรอรายงาน ad-hoc จากทีม data เฉลี่ย 2 วัน" ไม่ใช่ "อยากลอง AI"
2. **เกณฑ์ตัดสิน POC สำเร็จ** — วัดได้ เช่น: ตอบคำถามชุดทดสอบ 20 ข้อถูก ≥ 90%, ผู้ใช้ pilot ให้คะแนน ≥ 4/5, RLS ทดสอบผ่าน 100%
3. **ใครคือกรรมการ** — ผู้มีอำนาจตัดสินใจต้องเห็น demo ด้วยตาตัวเอง อย่างน้อย 1 ครั้ง

> 💡 POC ที่ไม่มีเกณฑ์สำเร็จเป็นลายลักษณ์ = POC ที่จบด้วย "ก็ดีนะ...เดี๋ยวดูอีกที" — เสียของทั้งสองฝ่าย

## Phase 1: เตรียมสนาม (สัปดาห์ที่ 1)

### ข้อมูล
- [ ] เลือก **published data source 1-2 ตัว** ที่: นิยามชัด, มี description, ข้อมูลสดพอ, ตอบ use case ได้
- [ ] ถ้าข้อมูลจริงอ่อนไหวเกินไป → สร้าง **synthetic dataset** โครงสร้างเหมือนจริง (แนะนำสำหรับ demo ผู้บริหารเสมอ — เดโมพลาดไม่มีข้อมูลจริงหลุด)
- [ ] เติม field description ให้ครบก่อน — ลงทุน 1 ชั่วโมงตรงนี้ ยกระดับคุณภาพคำตอบทั้ง POC

### ระบบ
- [ ] เลือกสถาปัตยกรรมตาม Cloud/Server (บท 1.4) — POC ใช้แบบง่ายสุดที่ตอบโจทย์: Hosted MCP (Cloud) หรือ npx (Server)
- [ ] Credential: PAT เฉพาะ POC สิทธิ์จำกัดที่ data source นำร่อง — **สร้างใหม่ อย่ายืมของ admin**
- [ ] `INCLUDE_TOOLS` เฉพาะ query พื้นฐาน
- [ ] เตรียม user ทดสอบ 2 คนสิทธิ์ต่างกันสำหรับ RLS test (บท 4.2)

### เนื้อหา
- [ ] **ชุดคำถามทดสอบ 20 ข้อ** จากเจ้าของ use case จริง (ไม่ใช่เราคิดเอง) — แบ่งง่าย 10 กลาง 7 ยาก 3 พร้อมเฉลยที่ verify กับ dashboard แล้ว
- [ ] Context priming / system prompt สำหรับข้อมูลชุดนี้ (บท 4.1)

## Phase 2: รันและเก็บหลักฐาน (สัปดาห์ที่ 2-3)

- [ ] รันชุดคำถาม 20 ข้อ → บันทึกผลเป็นตาราง: คำถาม | คำตอบ AI | เฉลย | ถูก/ผิด | หมายเหตุ
- [ ] ข้อที่ผิด: วิเคราะห์สาเหตุ (field กำกวม? prompt? ข้อจำกัด VDS?) และแก้ — ตารางนี้คือหลักฐานที่น่าเชื่อถือที่สุดใน final report
- [ ] รัน RLS 4 test cases → บันทึกผลพร้อม screenshot
- [ ] ให้ pilot users (3-5 คน) ใช้จริง 1 สัปดาห์กับงานของเขา → เก็บ feedback + ตัวอย่างคำถามจริงที่เขาถาม
- [ ] จดตัวเลขเชิงธุรกิจ: เวลาที่ประหยัดต่อคำถามเทียบ process เดิม

## Phase 3: Demo Day (เทคนิคจากสนามจริง)

**โครง demo 30 นาทีที่ได้ผล:**

```
0-5 นาที   ปัญหาเดิม — ยกตัวอย่าง request จริงที่รอ 2 วัน
5-15 นาที  Live demo 3 ฉาก:
           ① คำถามง่าย → ตอบใน 10 วินาที (ความเร็ว)
           ② คำถามเจาะต่อเนื่อง 3 ชั้น (ความลึก — จุดขายจริง)
           ③ ผู้บริหารถามสดเอง 1 คำถาม (ความเชื่อ)
15-20 นาที ความปลอดภัย: โชว์ RLS test — login 2 user เห็นต่างกัน
           (สไลด์เดียวที่ CFO/CISO อยากเห็นที่สุด)
20-30 นาที ผลตัวเลข POC + แผน rollout + คำขอตัดสินใจที่ชัดเจน
```

**กติกาป้องกัน demo พัง:**
- ซ้อมทุกคำถามในสคริปต์ ≥ 2 รอบเช้าวันจริง (PAT หมดอายุคืนก่อน demo = คลาสสิก! เช็ค!)
- ฉาก ③ เสี่ยงสุดแต่ตัดไม่ได้ — บริหารด้วยการ scope: "เชิญถามเกี่ยวกับยอดขายปี 2026 จากข้อมูลชุดนี้ครับ"
- เตรียมคำตอบ 3 คำถามที่โดนถามทุกครั้ง: ข้อมูลไปอยู่ไหน (บท 6.3 ข้อ 2), ผิดได้ไหม (โชว์ตาราง 20 ข้อ — ความโปร่งใสขายได้), ราคาเท่าไหร่ (เตรียมตัวเลข license + token ครัวเรือนจริง)

## Phase 4: Final Report (โครงพร้อมใช้)

1. Executive Summary — ผลเทียบเกณฑ์สำเร็จที่ตกลงไว้ (ข้อต่อข้อ)
2. ผลทดสอบความแม่น (ตาราง 20 ข้อ + อัตราถูกต้อง + สาเหตุข้อผิด)
3. ผลทดสอบความปลอดภัย (RLS report)
4. Feedback ผู้ใช้ pilot + ตัวอย่างคำถามจริง
5. ประมาณการต้นทุน scale จริง (license, infra, token, คนดูแล)
6. ความเสี่ยง + mitigation (ดึงจากบท 6.1/6.3)
7. ข้อเสนอ: Go / No-Go / Go-with-conditions + แผน Phase ถัดไป (rollout 3 phase จากบท 6.3)

## กับดัก POC ที่พบบ่อยสุด 5 อัน

1. **Scope บาน** — "ลองอีก data source สิ" ระหว่างทาง → ตอบว่า "จดไว้ Phase ถัดไปครับ" แล้วจดจริง
2. ใช้ข้อมูลที่ตัวเองไม่เข้าใจ → ตอบคำถามความถูกต้องไม่ได้กลาง demo
3. ข้าม RLS test เพราะ "แค่ POC" → โดนคำถาม security แล้วไปต่อไม่ได้
4. Demo ฉาก ③ โดยไม่ scope → เจอคำถามนอกข้อมูล AI ตอบเพี้ยนต่อหน้าผู้บริหาร
5. ไม่มีตัวเลขต้นทุน scale จริง → "น่าสนใจ แต่ขอไปดูงบก่อน" = ค้างเติ่ง
